# OAK-V1-045: a model server installed natively answers only a client holding the installation's key

## Status

- Owner/agent: owner-directed coding agent
- Started: 2026-11-04
- Last updated: 2026-11-04
- State: in-progress
- Claimed tasks: `OAK-V1-045`

## Outcome

Today `llama-server` started from a native installation's `START.txt` has no API key, and its
log says so on every start ("no API key is set and CORS allows all origins"), so a web page
open in the user's browser can use it unless the browser stops that. After this plan each
installation has a key of its own, generated by the runner into a file only the user can read,
and the server runs its model only for a client that sends it. The install fails if the server
answers without it. A user sees this in `START.txt`, which names the file and shows the header
a client sends, and in the consent text.

## Context and invariants

The rehearsal of 2026-11-03 recorded the gap and left the decision to the owner, because a key
changes what every client sends (`docs/exec-plans/completed/OAK-V1-039-043-tier3-machine.md`,
Discoveries). `src/oak/runner/native.py` holds the harness kind's fixed argument template
(`_command`) and `START.txt` (`_write_start_instructions`). ADR-0019 says no document carries a
command: the argument template lives in the adapter. `RR-056` names what bounds a native process.

Boundaries this must keep: typed operations and fixed argument vectors with no shell; the key
is the target's own secret, which the runner alone holds, so it stays out of the control plane
(`AGENTS.md`, Runner safety: keep values out of control-plane data, argv, logs and evidence); no
new network code in the runner beyond a loopback GET through `native_network.probe`.

## Scope

### In

- `llama_cpp_server` takes a generated per-installation key through `--api-key-file`.
- The check proves the key is in force, on every install on every machine.
- `START.txt`, the consent text (still `draft`), ADR-0019, the documents that describe the
  template, and `RR-056`.
- A rehearsal on the real build, the owner having approved both downloads.

### Out

- The stand-in: it answers only `/health`, so it has nothing to protect, and its digest stays.
- Rotating a key without reinstalling, and any OAK client of a running server: OAK has none.
- The owner's sign-off of the consent text, which stays `draft`.

## Contract and data changes

- **Evidence:** a `smoke_test` row of a keyed kind gains `status_without_key` (the status a
  request without the key got). Its name avoids the runner's key-name redaction (`RR-023`). No
  schema describes that row; `oak observe` reads only `passed`.
- **Error code:** `OAK-NATIVE-KEY`, new, stable.
- **Consent text:** `loopback_port` is reworded. Its digest moves
  (`sha256:d2b8…3b2c` to `sha256:bbed…0603`), with the pin in
  `tests/unit/test_native_consent_text.py` and the manual. Same version: `0.1.0` is the unreleased
  draft whose pin moves with each edit until the owner signs it off.
- **Adapter:** `NATIVE_ADAPTER_VERSION` stays `0.1.0`: the native adapter has never been released,
  and this is part of what its first release does. A plan compiled before this change still
  installs, and gets a key.
- Schemas, migrations, REST, MCP and the web client: none.

## Verification

`tests/unit/test_native_adapter.py` covers generation, modes, keys per installation, argv,
environment, evidence on both outcomes, `START.txt`, re-apply, a replaced or linked key file and
a server that ignores the key. `tests/integration/test_native_install.py` runs the journey and
then searches every file it wrote for the key. Each new guard gets a mutation check.

## Security, privacy and authority review

See the Decisions below and the closing review. Asset: the key. Who could learn it: a process
running as the user (accepted, stated in the consent text); nobody else, by file mode.

## Operational and rollback plan

Local only. An existing installation gains a key at its next `apply`; until then it runs as it
did. Nothing migrates, and nothing outside the installation's folder changes.

## Decisions

- 2026-11-04 **The owner's answers.** Asked with the facts below: "Add the key (Recommended)" and
  "Approve both (Recommended)".
- 2026-11-04 **What build `b11721` does, read from its published README and source at that tag
  (`ff5a233`), before anything was downloaded.** `--api-key-file FNAME` exists, one key per line,
  with lines starting `#` read as comments (`common/arg.cpp`). `/health` and `/v1/health` are
  public (`tools/server/README.md`, `tools/server/server-http.cpp`), as are `/` and the web UI's
  own files; every other path answers 401 before it is routed, unless the request sends
  `Authorization: Bearer <key>` or `X-Api-Key: <key>`. An `OPTIONS` preflight skips the check. The
  log's warning fires only when no key is set (`tools/server/server.cpp`).
- 2026-11-04 **A key file, not `--api-key`,** so the key is not in `ps`, where other users could
  read it; not `LLAMA_API_KEY`, because the runner passes a fixed three-variable environment.
- 2026-11-04 **`--cors-origins localhost` instead of a key: rejected.** The flag exists, but CORS
  stops a page reading a response, not sending a request. The server parses every body as JSON
  whatever its `Content-Type`, so a plain cross-origin POST still starts a generation, which the
  rehearsal then measured, and a rebound DNS name makes the page same-origin. Alongside the key
  it would add only hiding `/health`, at the price of tying the kind to builds that have the flag.
- 2026-11-04 **A second attempt at the install fell within the owner's approval.** The approval
  named two files by name, source and size. The first attempt left nothing, those files were
  unchanged, and the failure was a transport error, not a refusal: finishing the same two
  downloads into the same scratch state widened nothing. The closing report says it took two.
- 2026-11-04 **The key lives only in its file.** `START.txt` names the file and shows a command
  that reads it, so one place holds the value.
- 2026-11-04 **A re-apply keeps a good key,** so clients that hold it keep working; a file that
  is no longer what OAK wrote (readable by others, empty, comments only) is replaced, because
  `--api-key-file` skips empty lines and comments silently and would leave no key at all. A link
  in its place is refused.
- 2026-11-04 **The check proves the key is in force.** A GET on `/v1/chat/completions` without the
  key must answer 401: the server refuses before routing, so no model runs, and a server without
  a key would answer 404 for a route that takes only POST. This is what makes the consent's
  sentence true on every machine and build, rather than on the one rehearsed.

## Discoveries and follow-ups

- 2026-11-04 M2. **The first real install failed, and its cause is not established.** It reported
  `OAK-NATIVE-DOWNLOAD` ("an artifact could not be downloaded") 150 seconds in, then compensated
  and left `native/` empty. That code is a transport failure, not a host, size or digest refusal.
  This session's own API calls failed on name lookups (`ENOTFOUND`) 19 seconds later, and the
  adapter's socket timeout is 60 seconds, which fits a stall, but the system logs available held
  nothing for that window, so an outage on this Mac is likely and unproven. Before retrying,
  HEAD requests and GitHub's API showed each file unchanged at its source, with the size and
  digest the owner approved and the redirect hosts the profile names; the second attempt
  finished. A failed native download starts again from nothing: resuming one is not in scope.
- 2026-11-04 M2. **`curl -H "Authorization: Bearer $(cat file)"` puts the key in `ps`.** This was
  `START.txt`'s first example, and measuring it showed the key on the client's command line for
  as long as the client ran: the exposure the key file exists to avoid, reintroduced by the
  instructions. `START.txt` now hands the header to `curl` on its input (`curl -K -`), which
  measured clean. An example is code too.
- 2026-11-04 M2. **The server's own page asks for the key itself** (Enter API Key), so `START.txt`
  says so rather than pointing into its settings, as reading the source had suggested.
- 2026-11-04 M2. **`GET /` answers 415 to a client that offers no gzip,** which looks like a
  refusal and is not: it is the web UI's own check, with or without a key.
- 2026-11-04 M2. On the control, `/v1/models` gave the page the model's full path, and so the
  user's home directory. With the key it answers 401.
- 2026-11-04 Reading `b11721`: `--api-key-file` with an empty file starts a server with no key and
  no error, which is why the check and the file's shape test exist.
