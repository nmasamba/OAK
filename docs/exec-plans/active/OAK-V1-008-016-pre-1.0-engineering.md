# OAK-V1-008–016: the cheap, high-value engineering before 1.0

**Directed by the owner on 2026-10-23.** After the 1.0 readiness pass (`OAK-V1-001`–`007`,
PR #38, merged as `885c96a`) the owner asked for the remaining backlog ranked by cost and
benefit before 1.0; this plan does the cheap, high-value items from the top of that
ranking. It starts from `origin/main` at `885c96a`. It bumps no version, cuts no tag,
writes no decision record and publishes nothing.

## Status

- Owner/agent: owner-directed coding agent
- Started: 2026-10-23
- Last updated: 2026-10-23 (M6; M5 and M7 under way)
- State: in-progress
- Claimed tasks: `OAK-V1-008`–`OAK-V1-016`

One plan covers nine task IDs because they are one batch of small, independent fixes,
landed as one change and judged by one set of gates. They continue the release-readiness
series (`OAK-V1`), so the planned Sprint 15 keeps its number.

## Outcome

After this plan:

1. **CI runs the PostgreSQL-gated suites** (`OAK-V1-008`, closes `RR-019`): the `check`
   job starts a `postgres:17.6-alpine` service pinned by the digest `compose.yaml` uses,
   runs `oak-db-migrate`, and exports `OAK_TEST_DATABASE_URL`, so a green CI run is
   evidence that the database, tenant-isolation and interface-conformance suites ran.
2. **CI maintenance** (`OAK-V1-009`): both workflows use Node-24 releases of every action,
   each pinned by commit SHA with its version in a comment, and `make toolchain-check`
   refuses a workflow step that names an action by a movable tag. The tests no longer use
   the deprecated Starlette test client.
3. **The runner's trust boundary is narrower** (`OAK-V1-010`): `oak-runner` validates
   against the schemas bundled with it and ignores `OAK_SCHEMA_DIRECTORY` (`RR-033`);
   `docker` and `opa` are resolved once, at startup, to an absolute path on the absolute
   entries of `PATH`, every later call runs that path, and an `opa` older than `1.0.0` is
   refused (`RR-002`); both subprocess sites run their child in a private, empty,
   owner-only working directory that is removed afterwards (`RR-027`'s two runner
   clauses). `docs/signed-runner.md`'s verification order is unchanged.
4. **`/readyz` reports not ready** while the database's schema revision is not the one
   this binary was built for, in either direction (`OAK-V1-011`, closes `RR-016`).
5. **`oak keys show` only reads** (`OAK-V1-012`, closes `RR-018`): it reports the three
   identities, and refuses with `OAK-KEYS-UNINITIALIZED` when none exists; `oak keys init`
   is what creates them.
6. **CLI polish** (`OAK-V1-013`): `oak models set-key` checks `--store` before it asks for
   the secret; `oak policy packs` works outside a workspace; a `--server` URL ending in
   `/v1` is accepted; an unknown case on a server is reported as `OAK-CASE-NOT-FOUND`;
   `oak validate bundle` on an export directory says it was given an export; and
   `oak report --narrative online|local` without `--record` warns that the choice applies
   only when recording.
7. **The Report screen keeps the reader's place** (`OAK-V1-014`, Sprint 13's notes A-2,
   A-4, A-5): the pager's first and last buttons keep focus when they reach the end;
   the Take it sheet's Report tile, opened on the Report screen, closes the sheet and
   hands focus to the record control; recording refreshes the screen in place and moves
   focus to the first slide.
8. **The PDF renderer pins reportlab's settings** (`OAK-V1-015`): every `rl_config` value
   the canvas reads, and the standard fonts' encoding, are set inside the renderer, so an
   `RL_*` variable, a `reportlab_settings` module or `~/.reportlab_settings` cannot change
   the bytes; the two-process byte test sets `RL_*` variables in its child processes.
9. **Gates and the PR** (`OAK-V1-016`).

Demonstrated by: the tests named per milestone below; `make check` with
`OAK_TEST_DATABASE_URL` on a fresh, migrated throwaway PostgreSQL (port 15433) with zero
`make: ***` lines; `make audit` clean; `make web-e2e` on a throwaway Compose project with
its own name and ports; and the PR's CI green with the PostgreSQL suites running.

  `OAK-WORKSPACE-NOT-FOUND`).

- `oak policy evaluate --engine opa` refuses an `opa` older than `1.0.0`
  (`OAK-POLICY-ENGINE-UNAVAILABLE`).
- `/readyz` answers 503 while the database is not at this release's schema revision; a
  deployment that skipped `oak-db-migrate` was "ready" and then failed its first query.

## Verification

Each fix has a test on its failure path as well as its happy path, mutation-checked where
it is a new guard. Full gates once at the end: `make check` with `OAK_TEST_DATABASE_URL`
on a fresh, migrated PostgreSQL 17.6 (port 15433), `make audit`, `make web-e2e` on a
throwaway stack, and the PR's CI.

## Security, privacy and authority review

`OAK-V1-010` narrows what the runner's environment can change: the schema set it verifies
against, which binary it runs, and where that binary starts. `OAK-V1-012` removes a write
from a read. Nothing adds an authority, an egress or a stored datum. The new CI service
is a throwaway database with a CI-only password inside the job; no secret is used.

## Operational and rollback plan

Local-only change plus CI; each milestone is one commit and can be reverted alone. An
operator upgrading must run `oak-db-migrate` before readiness goes green (it was already
required, now it is visible), and run `oak keys init` where a script relied on
`oak keys show` to create keys.

## Decisions

- 2026-10-23 M0. **Action versions.** Each action moves to the newest release of its latest
  major that is at least two weeks old, pinned by its commit SHA: `actions/checkout` v7.0.1,
  `actions/setup-node` v7.1.0, `actions/upload-artifact` v7.0.2, `astral-sh/setup-uv`
  v10.2.0 (v10.3.x are under two weeks old) and `docker/setup-buildx-action` v4.4.1. Every
  one runs on Node 24 (checked in each pinned `action.yml`). The release notes between the
  old and new majors change nothing these workflows use: `setup-node` v6 limited
  *automatic* caching to npm, and these workflows ask for `cache: pnpm` explicitly;
  `setup-uv` v8 stopped publishing major tags (moot when pinned by SHA), v9 stopped pruning
  the cache by default, and v10 disabled `enable-cache: auto` for events these workflows
  never use (they set `enable-cache: true`).
- 2026-10-23 M0. **The remote CLI maps the unknown case; the server does not change.** A
  well-formed case id the server does not hold answers `OAK-WORKSPACE-NOT-FOUND` on REST and
  MCP (each server case is stored as its own workspace), while a malformed id answers
  `OAK-CASE-NOT-FOUND`, and the local CLI says `OAK-CASE-NOT-FOUND`. Changing the server
  would change a public REST and MCP denial pinned since Sprint 7; the owner asked for CLI
  polish, so the remote client maps a case route's `OAK-WORKSPACE-NOT-FOUND` to
  `OAK-CASE-NOT-FOUND` and names the case it was asked for. Whether REST and MCP should do
  the same at 1.0 is listed for the owner.
- 2026-10-23 M0. **OPA's minimum is `1.0.0`.** Every module the adapter generates is Rego v1
  (`import rego.v1`, `if`, `some … in`), and OPA `1.0.0` is the release that made Rego v1
  the language; the adapter has been exercised with `1.19.1` only. The divergence guard
  still refuses any version whose answers differ from the built-in engine; the floor
  refuses, by name, a binary too old to read the module at all.
- 2026-10-23 M0. **Readiness compares against a pinned head.** The expected revision is a
  constant beside the probe (`SCHEMA_REVISION`), and a test pins it to the head of the
  migration scripts, so adding a migration without moving the constant fails `make check`;
  the API reads no migration script at run time.
- 2026-10-23 M0. **`docker-config/` stays where it is.** The runner keeps its empty Docker
  client configuration at `$OAK_RUNNER_HOME/docker-config` (documented in three places);
  the new per-run working directory sits beside it and is removed at the end of each run.
