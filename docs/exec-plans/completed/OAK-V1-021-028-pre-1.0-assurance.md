## Outcome

After this plan:

1. **CI runs the browser suite** (`OAK-V1-021`, `RR-021`'s CI clause): a `web-e2e` job in
   `ci.yml`, beside `check`, builds the images from the commit, starts a Compose project
   named for the run on its own loopback ports with the research fixture on `api` and
   `worker`, checks that `/version` names the commit, installs the Chromium that the
   lockfile's Playwright pins, and runs the suite. Its known skips are named and counted:
   a skip that appears or disappears fails the job. It uploads no trace, screenshot or
   video. `release.yml` carries the same gate, and `make toolchain-check` refuses either
   workflow without it.
2. **A cut runner journal is noticed** (`OAK-V1-022`, `RR-054`): see M2 for where the
   comparison lives and what each place defends.
3. **CI proves a second platform** (`OAK-V1-023`, `RR-014`): a `macos-15` job on Apple
   silicon (Python and web paths, an asserted arm64 virtual environment, no Docker and no
   PostgreSQL, its skips counted) and an `ubuntu-24.04-arm` job (both images built natively
   for arm64, the PostgreSQL suites and the Docker journeys). `platforms.md` moves a row to
   "verified in CI" only for what a job runs.
4. **`oak-api` and `oak-worker` log** (`OAK-V1-024`, `RR-015`'s logging clause): one
   logging setup, JSON lines on stderr at `INFO` by default, with an access line per
   request naming the route template, status, duration and a request ID. Fields come from
   an allowlist. The MCP server logs only to stderr. A journey run with sentinels in every
   secret-bearing and user-content input proves that no sentinel reaches a log line.
5. **A local case can be moved onto a server** (`OAK-V1-025`): `oak --server import` of an
   export taken from a local workspace re-creates the case on the server from its brief
   and its confirmed answers, through the server's own design and confirm steps, linked to
   its origin. Nothing else from the export reaches the server: no approval, signature,
   tenant or later history.
6. **The PDF prints Latin, Greek and Cyrillic** (`OAK-V1-026`, `RR-046`'s Unicode clause):
   a vendored OFL-1.1 font, subset and pinned by SHA-256, with its licence in the wheel and
   the sdist; a character outside it renders as a visible, documented replacement. The
   output stays byte-stable across interpreters and `RL_*` environments. The tagging
   clause stays open (see Decisions).
7. **Release artifacts can be signed by the owner** (`OAK-V1-027`, `RR-005`): an
   `allowed_signers` file pins the owner's public SSH key, and `make verify-release` checks
   `SHA256SUMS.sig` with `ssh-keygen -Y verify`, failing closed for a release that must be
   signed. No agent creates the owner's key or signs anything.
8. **Review, gates and PR** (`OAK-V1-028`).

## Context and invariants

- **Assumptions.** The repository is public, so GitHub's `macos-15` and `ubuntu-24.04-arm`
  runners cost nothing. GitHub's macOS runners have no Docker, and `services:` containers
  run only on Linux. The installed reportlab (5.0.1) cannot write a structure tree.
- **Invariants.** No production readiness claim. No authority bypass: MCP stays design and
  read only, the remote CLI keeps refusing local-only commands, runner apply stays behind
  signing, approval, enrollment and the runner's own verification. No `command`, `shell`,
  `executable` or `argv` field in a canonical document. The import boundaries hold
  (`tools/check_boundaries.py`). The four reference digests and the report's JSON golden
  do not move; only `OAK-V1-026` changes the PDF's bytes, deliberately, recorded in the
  changelog. Verification uses pinned keys and published digests, never a value carried
  inside the artifact being checked. `make check` keeps working offline after bootstrap;
  CI jobs may download browsers and images. Logs never carry a secret or user content. The
  OpenAPI baseline changes only by additive operations listed as unreleased. `make check`
  is judged by counting `make: ***` lines, never two at once. The owner's `oak-community`
  Compose stack (5173, 8080) and its database (15432) are never touched. `tests/live` is
  never run with `OAK_LIVE_MODEL_TESTS=1`. `docs/error-codes.md` is regenerated after every
  `src/` edit. No AI-vendor attribution in commits or the PR.
- **Recipes** (`skills.md`): Dependency and release (CI jobs, the font, signing); Security
  review (logging, import, signing, the journal); Runner safety and Contract change (the
  journal comparison); Interface adapter and Domain use case (local to server); Compiler
  stage's determinism rule (the PDF); Documentation and ADR throughout.

## Security, privacy and authority review

By milestone, as the two reviews left it (their tables below hold each finding):

- **M1, the browser suite.** It runs on a Compose project of its own, on loopback ports,
  never the owner's stack (`check_target` refuses the reserved names and ports); it
  uploads nothing, its checkout keeps no token, and no expression in the job or the
  workflow-wide settings names a secret, because a failed page's trace can show a brief
  or a key field (R1-11).
- **M2, the journal.** `status` believes only completions its own key signed, ties a
  journal to them three ways, lists what no journal claims, refuses to compare without its
  key (R1-4), and survives anything dropped in the untrusted mailbox (R1-12). What
  remains is the runner's key holder, who can sign a cut head; ingest's accepted record,
  out of the runner's reach, never rewinds.
- **M3, the platforms.** Each job proves where it ran by an asserted platform, and counts
  its skips; nothing can turn a gate step into a no-op without `make toolchain-check`
  refusing it (R1-5, R3-5).
- **M4, logging.** Lines are built from an allowlist; an exception is its type and code;
  the sentinel journey covers the API and worker inputs, and the allowlist covers the rest
  (R2-13). `oak serve`'s token line is the interactive command's, deliberately (R1-9).
- **M5, local to server.** Nothing with authority crosses: re-creation replays only the
  brief and the digest-checked answers under the importing command's actor and tenant; the
  restore path refuses authority records; malformed objects are stable refusals (FC-7,
  R1-14). The restored history's actors are a recorded follow-up.
- **M6, the PDF.** The fonts are pinned by digest and refused if a different font holds
  their names (R1-18); rendering is serialised (R1-1); no setting or variable in the
  environment reaches a byte (R1-6, R2-11). Fonts are parsed by reportlab's `TTFont`, a
  new parser surface over files the repository pins.
- **M7, signing.** The policy never comes from the artefact (FC-1); the key never comes
  from the download, compared by file identity (R2-9); revocation works because
  consumers take the key file from `main` (R2-3).

## Decisions

- 2026-10-28 M0. **The owner's kickoff answers**, asked together at the start with options
  and a recommendation each:
  - **Q1, signing:** an owner-held SSH key, offline. The owner signs `SHA256SUMS` with
    `ssh-keygen -Y sign -n file`, the public key is pinned as `allowed_signers`, and
    `make verify-release` checks it. Sigstore was not chosen.
  - **Q2, the PDF:** a bundled font covering Latin, Greek and Cyrillic, which reverses
    Sprint 13's K5 ("no font file ships"). The installed reportlab cannot write a structure
    tree, so the tagging clause of `RR-046` stays open with a PDF/UA pass planned after 1.0;
    no structure tree is hand-rolled.
  - **Q3, local to server:** guided re-creation. A local export is re-created on the server
    from its brief and confirmed answers through the server's own steps, linked to its
    origin; it carries no later history. Scouting before the question found that the
    workspace identity is bound in storage (the manifest and the database rows) and, for a
    case compiled against a mutation-capable target, inside its runner plan as
    `oak.community/installation_scope`, so inside that plan's digest, its signature, any
    approval of it and the runner's installation identity. Audit events carry the tenant
    and the case, not the workspace.
  - **Q4, logging:** JSON lines on stderr, default level `INFO`, the access log on by
    default.
  - **Q5, platforms:** both a `macos-15` job and an `ubuntu-24.04-arm` job.
- 2026-10-28 M1. **The browser suite runs through one script, not workflow steps.** The
  six steps the prompt lists (build, start a project named for the run on its own ports
  with the research fixture, wait for health, check `/version`, install Chromium, run) are
  `scripts/run_browser_suite.py` plus one install step, so CI, the release gate and a

## Discoveries and follow-ups

- **A server-shaped import restores its history as written.** A server export, or a
  relabelled local one without authority records, is restored with its audit events'
  actors and interface origins as the export states them; the file adapter checks
  digests, the chain and the tenant, not who acted. This predates the batch and is not
  authority (the server has no approval or dispatch path), but a forged actor in restored
  history would read as genuine. A follow-up should either re-create server exports too or
  record the importer on restore.

## Self-review

- **What the review caught that the milestones did not.** The highest finding was mine to
  have avoided: M7 read "is a signature required?" from a file name inside the download,
  which is the attacker's to choose. Its tests passed because they only ever named the
  wheels honestly. The lesson is the one the prompt states, applied to a version: a
  verifier must not take its policy from the artefact it verifies.
- **Two of the leaks were older than the batch** (the eager app import, the
  `OAK-SAFE-BIND: {error}` echo), but the batch's own claim, that no message or traceback
  reaches a log, made them false, so they were fixed here rather than listed.
- **Item 5's restore path** carried a pre-existing way round the batch's invariants
  (relabelling `manifest.id`). The refusal closes the authority half; the restored audit
  history's actors are recorded as a follow-up, not fixed, because changing what a server
  restore keeps is a decision about portability the owner should take.
- **Honesty about CI.** RR-014 was closed one commit before its expectations had passed CI;
  the runs that prove it are now named in Progress. Every "Verified in CI" row was checked
  against a job's log, not its tick.
- **What is not done.** The PDF's structure tree, metrics, web unit tests and the owner's
  key are out of scope or the owner's; each register entry says what remains.
- **What the second review caught.** The first review read the diff before M6 existed, so
  the font change, which turned a stateless renderer into one sharing objects across
  threads, was never read by anyone but its author. The race needed a reviewer to think
  about the API's thread pool, not the renderer. Most of the rest was documentation the
  fixes had overtaken: a claim written once ("from 1.0.0", "only the PDF's bytes", "every
  input") outlived the code that made it true. Review the finished diff, not a milestone
  of it.
