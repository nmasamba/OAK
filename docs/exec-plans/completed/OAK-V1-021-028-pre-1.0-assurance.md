## Outcome

After this plan:

1. **CI runs the browser suite** (`OAK-V1-021`, `RR-021`'s CI clause): a `web-e2e` job in
   `ci.yml`, beside `check`, builds the images from the commit, starts a Compose project
   named for the run on its own loopback ports with the research fixture on `api` and
   `worker`, checks that `/version` names the commit, installs the Chromium that the
   lockfile's Playwright pins, and runs the suite. Its known skips are named and counted:
   a skip that appears or disappears fails the job. It uploads no trace, screenshot or
   video. `release.yml` carries the same gate, and `make toolchain-check` refuses either
   workflow without it.
2. **A cut runner journal is noticed** (`OAK-V1-022`, `RR-054`): see M2 for where the
   comparison lives and what each place defends.
3. **CI proves a second platform** (`OAK-V1-023`, `RR-014`): a `macos-15` job on Apple
   silicon (Python and web paths, an asserted arm64 virtual environment, no Docker and no
   PostgreSQL, its skips counted) and an `ubuntu-24.04-arm` job (both images built natively
   for arm64, the PostgreSQL suites and the Docker journeys). `platforms.md` moves a row to
   "verified in CI" only for what a job runs.
4. **`oak-api` and `oak-worker` log** (`OAK-V1-024`, `RR-015`'s logging clause): one
   logging setup, JSON lines on stderr at `INFO` by default, with an access line per
   request naming the route template, status, duration and a request ID. Fields come from
   an allowlist. The MCP server logs only to stderr. A journey run with sentinels in every
   secret-bearing and user-content input proves that no sentinel reaches a log line.
5. **A local case can be moved onto a server** (`OAK-V1-025`): `oak --server import` of an
   export taken from a local workspace re-creates the case on the server from its brief
   and its confirmed answers, through the server's own design and confirm steps, linked to
   its origin. Nothing else from the export reaches the server: no approval, signature,
   tenant or later history.
6. **The PDF prints Latin, Greek and Cyrillic** (`OAK-V1-026`, `RR-046`'s Unicode clause):
   a vendored OFL-1.1 font, subset and pinned by SHA-256, with its licence in the wheel and
   the sdist; a character outside it renders as a visible, documented replacement. The
   output stays byte-stable across interpreters and `RL_*` environments. The tagging
   clause stays open (see Decisions).
7. **Release artifacts can be signed by the owner** (`OAK-V1-027`, `RR-005`): an
   `allowed_signers` file pins the owner's public SSH key, and `make verify-release` checks
   `SHA256SUMS.sig` with `ssh-keygen -Y verify`, failing closed for a release that must be
   signed. No agent creates the owner's key or signs anything.
8. **Review, gates and PR** (`OAK-V1-028`).

## Context and invariants

- **Assumptions.** The repository is public, so GitHub's `macos-15` and `ubuntu-24.04-arm`
  runners cost nothing. GitHub's macOS runners have no Docker, and `services:` containers
  run only on Linux. The installed reportlab (5.0.1) cannot write a structure tree.
- **Invariants.** No production readiness claim. No authority bypass: MCP stays design and
  read only, the remote CLI keeps refusing local-only commands, runner apply stays behind
  signing, approval, enrollment and the runner's own verification. No `command`, `shell`,
  `executable` or `argv` field in a canonical document. The import boundaries hold
  (`tools/check_boundaries.py`). The four reference digests and the report's JSON golden
  do not move; only `OAK-V1-026` changes the PDF's bytes, deliberately, recorded in the
  changelog. Verification uses pinned keys and published digests, never a value carried
  inside the artifact being checked. `make check` keeps working offline after bootstrap;
  CI jobs may download browsers and images. Logs never carry a secret or user content. The
  OpenAPI baseline changes only by additive operations listed as unreleased. `make check`
  is judged by counting `make: ***` lines, never two at once. The owner's `oak-community`
  Compose stack (5173, 8080) and its database (15432) are never touched. `tests/live` is
  never run with `OAK_LIVE_MODEL_TESTS=1`. `docs/error-codes.md` is regenerated after every
  `src/` edit. No AI-vendor attribution in commits or the PR.
- **Recipes** (`skills.md`): Dependency and release (CI jobs, the font, signing); Security
  review (logging, import, signing, the journal); Runner safety and Contract change (the
  journal comparison); Interface adapter and Domain use case (local to server); Compiler
  stage's determinism rule (the PDF); Documentation and ADR throughout.

  - **Q3, local to server:** guided re-creation. A local export is re-created on the server

  - **Q4, logging:** JSON lines on stderr, default level `INFO`, the access log on by

  - **Q5, platforms:** both a `macos-15` job and an `ubuntu-24.04-arm` job.
- 2026-10-28 M1. **The browser suite runs through one script, not workflow steps.** The
  six steps the prompt lists (build, start a project named for the run on its own ports
  with the research fixture, wait for health, check `/version`, install Chromium, run) are
  `scripts/run_browser_suite.py` plus one install step, so CI, the release gate and a
  developer (`make web-e2e-isolated`) run the same tested code. The Compose override is
  written at run time, because `!override` is a tag a YAML safe loader refuses and the
  original spec repo's validator safe-loads every YAML file under both repositories.
- 2026-10-28 M1. **`/version` names the commit because the image carries it.** Setting
  `OAK_COMMIT` in the override's environment would only prove the variable was passed, so
  a stale image could still answer. The API image now takes `OAK_COMMIT` as a build
  argument (last in the Dockerfile, so it rebuilds nothing above it) and the script passes
  the commit it builds; a build that passes none reports `unknown` as before.
- 2026-10-28 M1. **What a failed run uploads: nothing.** A failed page's trace or screenshot
  can show a brief or a model-key field, and Playwright's error text quotes the page. The
  job uploads no artifact and reads no secret, and `make toolchain-check` refuses either.
  The list reporter's output in the public job log carries only the suite's synthetic
  fixtures, because the job has no secret to leak. Debugging a CI-only failure therefore
  means reproducing it with `make web-e2e-isolated`, which keeps the report locally.
- 2026-10-28 M1. **Skips are named, not counted.** The script fails unless the skipped tests
  are exactly the two manual captures (`EXPECTED_SKIPS`), so a new skip or a capture that
  starts running both fail; any test that did not pass cleanly (failed, flaky, timed out,
  interrupted) fails, and no retries are configured.
- 2026-10-28 M1. **`RR-021`'s unit-test clause stays open**, as the prompt scopes it: the
  register row says which clause closed.
- 2026-10-28 M2. **The comparison lives in both places, and each says what it defends.**
  Journals are one per dispatch, not one per runner, so "the last journal accepted from
  that runner" means the last completion accepted for the same lease. On the runner,
  `oak-runner status` compares each journal with the newest completion for its dispatch
  still in the mailbox (unacknowledged or acknowledged), believing only one its own key
  signed: this notices a cut made by anyone, or anything (a restored backup, a clean-up),
  that did not also remove the completions, but not one made by whoever holds the key and
  the mailbox. On the control plane, `oak ingest` keeps every accepted completion out of
  the runner home's reach and refuses a completion for the same lease whose journal is
  shorter, or as long with another last entry: the accepted record never rewinds, and a
  runner that reports again from a cut journal is refused rather than believed.
- 2026-10-28 M2. **A sequence, not only a digest.** A digest cannot show that one journal
  extends another; the head's sequence can show that one is shorter. A longer journal is
  believed to extend the earlier one on the runner's signature over both; proving it would
  need every intermediate digest, which the completion does not carry.
- 2026-10-28 M2. **No schema change.** The completion payload is an open object in
  `runner-message.schema.json` (only the four execution field names are refused), so
  `journal_sequence` is additive there. A `0.9` runner's completion still ingests, unless an
  earlier completion for the same lease named a sequence (`compatibility.md`).
- 2026-10-28 M2. **Refusals say why.** `IngestResult` gains `refused` (message id and code)
  and `oak ingest` prints it, because a rejected id alone did not say whether the message
  was unsigned or rewound.
- 2026-10-28 M3. **Skips are pinned by reason and count, per job.** A count per reason, not
  only an allowed set of reasons, because a test that newly skips under an allowed reason
  is also a narrowing of what the job proves. The price: adding a PostgreSQL-gated test
  means raising the macOS job's count in `tests/expected-skips.json`, and the job says so.
  The ledger is written by `tests/conftest.py` and unset inside each test, so a test that
  calls the summary hook with made-up reports cannot write into CI's ledger.
- 2026-10-28 M3. **Platform rows moved only for what a job runs.** macOS arm64's CLI row and
  both Linux rows' CLI and signed-runner columns are "Verified in CI": the Linux jobs run
  the real-daemon runner journeys (43 end-to-end tests, none skipped). Linux x86_64's
  signed-runner column was "Expected" although CI's `check` job already ran those journeys;
  it moves with arm64's. No control-plane column moves: CI starts no Compose installation an
  operator would run (the `web-e2e` stack is a test fixture), and macOS CI has neither
  PostgreSQL nor Docker.
- 2026-10-28 M4. **What a log line may carry, and why not tenant or actor.** Fields come
  from `ALLOWED_FIELDS`, and string values must be identifier characters, so prose cannot
  ride in even through an allowed field. The tenant and the actor are left out: either can
  name a person or an organisation, and the minted request ID, returned to the caller,
  joins a line to the audit trail, which records both under its own controls. The case ID
  is left out because it is named from the brief. Message arguments, exception messages and
  tracebacks are never rendered; a library's record is its logger and level only.
- 2026-10-28 M4. **The request ID is minted, not taken from `X-Correlation-ID`.** That
  header is client text (8 to 160 characters of anything), so logging it would log what a
  client chose to put there.
- 2026-10-28 M5. **The answers are recovered, not stored.** Confirming keeps each answer's
  question, decision, rationale and a digest of its value, and writes the value into the
  intent; no answers document is kept. Each value is therefore read from the intent version
  its round produced (for `reject`, `null` or the value it removed are tried) and used only
  if it hashes to the recorded digest. Rounds are replayed one by one, because a later
  round can answer a question an earlier one reopened.
- 2026-10-28 M5. **What is refused before anything is created.** A case interpreted with a
  model (the server would have to repeat a model run whose answer can differ), an answer
  that cannot be recovered exactly, a broken intent chain, an export claiming another
  tenant, edited digests and a case id the server already holds. A step the server itself
  refuses later (a question that is no longer open, for an export from another OAK version)
  stops the replay where it stands and says how far it got (`OAK-IMPORT-REPLAY`).
- 2026-10-28 M5. **The export's tenant must match the command's.** Re-creation could have
  ignored the claim, since only the brief and the answers cross, but refusing it keeps the
  rule the server-shaped import already had and keeps the claim out of the decision.
- 2026-10-28 M5. **The origin is recorded right after the case is created**, before the
  replayed steps, so a replay that stops part-way still says where its case came from.
- 2026-10-28 M7. **How a release from before signing still verifies.** Signatures are
  required when the one wheel the manifest lists is `1.0.0` or later (pre-releases of
  `1.0.0` included), or when no wheel version can be read; `0.7.1` and `0.9.0` verify by
  checksum and say they are unsigned. Relabelling a `1.0` wheel as `0.9.x` to dodge the
  rule would need a rebuilt wheel, because pip refuses a wheel whose file name and metadata
  disagree, and would name a release that does not exist.
- 2026-10-28 M7. **The namespace is `oak-release`, not `file`.** The prompt's example used
  `-n file`; a project namespace means a signature the key made for any other purpose does
  not verify as a release.
- 2026-10-28 M7. **The release workflow checks checksums only.** The maintainer signs after
  `release.yml` builds, so a signature cannot exist there; the consumer-side
  `make verify-release` requires it. This is a `.github/` change.
- 2026-10-28 M7. **Where the key lives.** `keys/allowed_signers` at the repository root,
  read from the release's tag; the verifier refuses a key file inside the directory it
  verifies, so the sdist's or a download's copy is never used.
- 2026-10-28 M6. **IBM Plex, from IBM's own repository.** The workspace already uses it
  (Sprint 12's font review), it is OFL-1.1, and Plex Sans covers Latin, Greek and Cyrillic.
  Plex Mono has no Greek; monospaced text is identifiers and digests, ASCII by
  construction, so a Greek letter there prints as U+FFFD. The files were fetched only after
  the owner approved the five named files, sources and sizes.
- 2026-10-28 M6. **The renderer keeps its recorded identity.** `oak-report-renderer 1.0.0`
  is recorded inside the report document, so a new version would move the JSON golden,
  which the prompt pins. The PDF's own Creator says ", IBM Plex" instead, and the changelog
  and `compatibility.md` record that one renderer version now has two outputs.
- 2026-10-28 M6. **Tagging stays open.** reportlab 5.0.1's open-source build has no marked
  content or structure tree writer; per the owner's Q2b answer, no structure tree is
  hand-rolled and `RR-046` keeps the tagging clause, with a PDF/UA pass after 1.0.
- 2026-10-28 M6. **Old recordings still verify.** Nothing draws a recorded report again: the
  PDF is drawn once, when the report is recorded, stored as `report_rendering` and served
  as stored, digest-checked like any artifact.
- 2026-10-28 M8. **Superseding M7: unsigned releases are known by digest, not version.** The
  review showed a version read from a downloaded file name is the attacker's to choose.
  `UNSIGNED_RELEASES` pins the SHA-256 of the `SHA256SUMS` published for 0.7.1 and 0.9.0,
  taken from the digests GitHub reports for those release assets; everything else must be
  signed. The plan's earlier "required from 1.0.0" wording describes the same releases, but
  the rule no longer reads a version.
- 2026-10-28 M8. **Authority records never restore on a server.** Rather than trust
  `manifest.id`, the restore path refuses the seven kinds only the local release service
  writes. A genuine server export never holds one, so nothing that worked before stops.
- 2026-10-28 M8. **One API process.** uvicorn workers would each need the allowlisted
  logging; OAK Community runs one process anyway, so `workers=1` is pinned rather than
  passing a logging configuration to each worker.
- 2026-10-28 M0. **The owner deferred Tier 1's owner half** (the K2 variant rename, the
  harness-list review, the `@role` owner names) until the 1.0 launch.

## Discoveries and follow-ups

- **A server-shaped import restores its history as written.** A server export, or a
  relabelled local one without authority records, is restored with its audit events'
  actors and interface origins as the export states them; the file adapter checks
  digests, the chain and the tenant, not who acted. This predates the batch and is not
  authority (the server has no approval or dispatch path), but a forged actor in restored
  history would read as genuine. A follow-up should either re-create server exports too or
  record the importer on restore.

## Self-review

- **What the review caught that the milestones did not.** The highest finding was mine to
  have avoided: M7 read "is a signature required?" from a file name inside the download,
  which is the attacker's to choose. Its tests passed because they only ever named the
  wheels honestly. The lesson is the one the prompt states, applied to a version: a
  verifier must not take its policy from the artefact it verifies.
- **Two of the leaks were older than the batch** (the eager app import, the
  `OAK-SAFE-BIND: {error}` echo), but the batch's own claim, that no message or traceback
  reaches a log, made them false, so they were fixed here rather than listed.
- **Item 5's restore path** carried a pre-existing way round the batch's invariants
  (relabelling `manifest.id`). The refusal closes the authority half; the restored audit
  history's actors are recorded as a follow-up, not fixed, because changing what a server
  restore keeps is a decision about portability the owner should take.
- **Honesty about CI.** RR-014 was closed one commit before its expectations had passed CI;
  the runs that prove it are now named in Progress. Every "Verified in CI" row was checked
  against a job's log, not its tick.
- **What is not done.** The PDF's structure tree, metrics, web unit tests and the owner's
  key are out of scope or the owner's; each register entry says what remains.
