# Residual risk register — OAK Community 0.9.0 and unreleased work on main

What this release does **not** defend against, in one place, with stable identifiers.

Until now these were scattered across three completed sprint plans with no ids, no
severities and no links to the threats or invariants they touch. Anything documented in a
sprint post-mortem was effectively undiscoverable to a user of the software, which is the
wrong place for a statement about what a release does not protect.

**Every entry here is a known gap, not a discovered vulnerability.** The `0.9.0` decision
record accepted `RR-001` to `RR-043`; `RR-044` to `RR-054` describe the unreleased report
and research work and are accepted by no release decision yet. For
reporting something not on this list, see [SECURITY.md](../../SECURITY.md).

## How to read this

- **Severity** is scored *for the shipped configuration* — a local-first developer
  release whose runner reaches only an explicitly acknowledged fixture profile and whose
  keys are labelled `development`. Several entries would be materially more severe in a
  deployment Community does not support, and say so.
- **Owner** is unassigned for every entry. Assigning owners is part of the release
  decision and requires accountable humans; see
  [release/0.9.0/release-decision.md](../release/0.9.0/release-decision.md).
- **Blocks release** records whether the entry is proposed as a P0 blocker. That
  proposal is a recommendation to the maintainers, not a decision taken here.

## Register

### Signing, approval and the runner

| ID | Risk | Severity | Blocks release | Source |
|---|---|---|---|---|
| `RR-001` | ~~Revocation notices are unsigned and the channel is fail-open.~~ **Closed 2026-08-24; completed 2026-08-25 after the closing audit.** Notices are signed in the `approver` role against `revocation.schema.json`, and a signed **revocation manifest** (`revocation-manifest.schema.json`) inventories the complete set by canonical digest with a strictly monotonic sequence the runner records in its own home. The audit showed the first fix was incomplete — deleting one *valid* notice from a healthy directory still restored its approval — so the runner now refuses any notice set that does not match the manifest exactly, any manifest whose sequence regresses below the recorded high-water mark, a missing manifest on a dispatched mailbox, and (as before) a missing directory or any unreadable, oversized, malformed or unsigned entry (`OAK-RUNNER-REVOCATION`). Every one of those attacks, including single-notice deletion and set rollback, is a regression test in `tests/integration/test_runner_revocation.py`. The one window that remains is inherent: a rollback the runner has never observed newer state than is indistinguishable from delivery never having happened. The 1.0 readiness review found the control-plane side still trusted the mailbox: a later revocation re-signed whatever notices the directory held, so deleting one and waiting for the next revocation restored the approval. Each manifest now keeps every entry the last signed one listed, and a manifest this control plane did not sign is refused before anything is revoked (`tests/integration/test_runner_trust_boundary.py::test_a_deleted_notice_stays_in_the_next_signed_manifest`). | Closed | No | Sprint 5 |
| `RR-002` | ~~`docker` and `opa` are resolved through the inherited `PATH` on every call, and no minimum OPA version is enforced.~~ **Closed 2026-10-23.** Each is resolved once, when the runner starts a run or the OPA engine is built, to an absolute path on the absolute entries of `PATH` (a relative entry such as `.` is skipped), and every later call runs that path, so a change to `PATH` or to what it reaches part-way through cannot swap the binary. An `opa` older than `1.0.0`, the release whose Rego the generated module is written in, or one that reports no version, is refused with `OAK-POLICY-ENGINE-UNAVAILABLE` before anything is evaluated (`tests/unit/test_runner_environment.py`, `tests/unit/test_opa_engine.py`). What remains is trust in the `PATH` a process starts with, the same trust as in the rest of its environment; the child still sees only `os.defpath`. | Closed | No | Sprints 5–6 |
| `RR-003` | ~~The image digest is not verified against what the container runtime actually resolved, and no registry allowlist exists.~~ **Closed 2026-08-24.** After `docker create`, and for every container it adopts, the adapter requires a `RepoDigests` entry carrying the approved digest. A mismatch, a missing identity or an inspect failure denies the install (`OAK-RUNNER-IMAGE`). The install's compensation then removes the container if that install created it, and leaves one that was already there for the operator. A target profile may declare `execution.allowed_registries`, enforced for every container during verification before any adapter exists (`OAK-RUNNER-REGISTRY`), and both shipped mutation profiles allowlist `docker.io`. The time-of-use half of TM-08 is now enforced — see [threat-coverage.md](threat-coverage.md). This was the other standing condition on the `0.7.0` approval. | Closed | No | Sprint 5 |
| `RR-012` | The runner's trust-anchor directory defaults to the same path that holds the control plane's **private** signing keys (`~/.oak/trust`). Only `*.identity.json` files are read, but the two concerns share a directory. | Medium | Proposed: no | Sprint 5 |
| `RR-013` | The runner's Docker child sees only `PATH` and an empty, runner-owned `DOCKER_CONFIG`. `HOME`, `DOCKER_HOST`, `XDG_RUNTIME_DIR` and `TMPDIR` are not passed, and the operator's `~/.docker/config.json` is never used: not its registry credentials, its credential helpers or its CLI contexts. Only a daemon on the default socket is reachable, and images are pulled anonymously. Rootless Docker, Colima and Podman socket shims are not supported. Neither is a non-default Docker context, or an acknowledged image in a registry that requires credentials. | Low (availability, not security) | No | Sprint 8; extended in Sprint 11 |
| `RR-023` | **Runner evidence redaction is a pattern list.** Since Sprint 11 evidence is redacted by key as well as by value. A field named like a secret (`password`, `secret`, `token`, `api_key`, `authorization`, `credential`, `private_key`, `connection_string`, `dsn`, `cookie`, `env`, `environment`, or one of the plan's `redact_fields`) is withheld at any depth, whatever its value. A credential inside a URL (`scheme://user:password@host`) is withheld too (`tests/unit/test_runner_evidence_redaction.py`). Adapter output now reaches evidence, because the topology installer reads `docker inspect` and `docker stats`. It arrives only as parsed typed fields: a container state and health from a fixed vocabulary, an exit code, startup seconds and a memory figure. No log, environment or raw output reaches evidence. What remains is that both checks match patterns, so a secret held under an unrecognised key, in a value of no recognised shape, would pass. No current adapter field can carry one. A `model_proposed` rationale still never reaches runner evidence. | Low | No | Sprint 8; re-scored in Sprint 11 |
| `RR-027` | ~~Three security-invariant clauses were neither enforced nor recorded as exceptions: no isolated working directory for the runner's children, no workspace zeroization, and a silent non-loopback bind.~~ **Closed 2026-10-23.** Both subprocess sites now start their child in a private, owner-only directory that is removed afterwards (empty for the runner; holding only the generated module for OPA): `oak-runner run-once` makes one per run under `$OAK_RUNNER_HOME` (and removes any a crashed run left before it starts), and the OPA engine makes one per evaluation (`tests/unit/test_runner_environment.py::test_each_run_works_in_a_private_directory_that_is_removed_after_it`, `tests/unit/test_opa_engine.py`). The runner resolves no secret, so that directory is the whole of its working state; what it keeps on purpose (journals, the nonce ledger, processed dispatches and the empty `docker-config/`) is evidence the retention contract keeps, and `RR-031` records that nothing reclaims it. Since Sprint 9 `oak-api` warns on a non-loopback bind, naming the `Host` allowlist. | Closed | No | Sprint 8 |
| `RR-032` | ~~The compiled verification policy's `mutation_allowed` and `allowed_operation_kinds` clauses are not enforced.~~ **Closed 2026-08-24** by the deliberate digest migration recorded in `CHANGELOG.md` `0.7.1`: the compiled policy is now derived from the target profile (id, allowed kinds, mutation flag), and the runner denies any requested kind outside `allowed_operation_kinds`, any mutating kind under `mutation_allowed: false`, and any malformed clause (`OAK-RUNNER-POLICY`) before any adapter exists. An authentically signed restrictive policy denying a fully approved mutation is a regression test in `tests/integration/test_signed_runner.py`. | Closed | No | Sprint 8 |
| `RR-033` | ~~`OAK_SCHEMA_DIRECTORY` crosses the runner's trust boundary.~~ **Closed 2026-10-23.** The runner validates the target profile, envelope, lease, approval and signature documents only against the schemas installed with it (`src/oak/runner/schemas.py`) and no longer reads the variable, so its environment cannot substitute the rules it verifies against (`tests/unit/test_runner_environment.py::test_the_runner_verifies_against_its_bundled_schemas_whatever_the_environment_says`). The control plane still honours it. | Closed | No | Sprint 8 |
| `RR-029` | The signature block's own `role` and `trust_level` fields sit outside the signed payload. Anchor-based verification makes a mismatch unusable, but the fields remain unauthenticated claims. | Low | No | Sprint 5 |
| `RR-043` | **A profile that acknowledges starting runs processes from pinned images on the operator's machine.** On a target profile whose `execution.mutation_acknowledgement` is `isolated-non-production-hardened-start`, the signed, approved `apply` starts one container per selected node. Each container's image is the one the profile maps to that component in `execution.component_images`, and that image's own entrypoint runs until rollback, destroy or manual removal. What bounds it: (1) The image is the operator's acknowledgement: pinned by digest, allowlisted by registry, and checked against the runtime's resolved `RepoDigests`. (2) Each container runs with `--network=none`, a read-only root, every capability dropped, `no-new-privileges` and uid 65534. Memory is 256 MiB with no swap, CPU is half a core, processes are capped at 64, and `--restart=no` and no log driver are set. It has no volumes, environment or ports. (3) Two separately signed approvals come first: the architecture, then the installation. (4) Before anything is adopted or started, the runner reads each container's configuration back from the daemon and refuses one whose network or hardening differs from what was approved (`OAK-RUNNER-ISOLATION`). (5) A failed smoke test removes what that apply created, and rollback or destroy removes only containers that carry this installation's labels. What does not bound it: the code inside the image, which OAK neither builds nor inspects; the shared host kernel and container runtime, so an escape vulnerability sits outside every flag above; and the daemon on the default socket, which runs with whatever privileges the operator gave it. The shipped profiles map every component to a pause image whose process only waits. An operator who maps a component to another image accepts what that image does. Profiles acknowledging `isolated-non-production-fixture-only` never start anything. | Medium — opt-in per profile, bounded by the hardening flags | Proposed: no | Sprint 11; ADR-0017 |

**`RR-001` and `RR-003` history.** Both were accepted for the `0.7.0` approval *only
because of what that release actually permitted* — one network-isolated, never-started
fixture container on the operator's own machine — with the standing condition that both
become P0 before any release that permits a runner off that machine or a non-fixture
target. Nothing was ever published under `0.7.0`, and the pre-launch hardening closed
both before first publication, while the protocol changes were still free. The condition
is discharged by the closures, not by reinterpretation.
