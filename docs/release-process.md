# Release process

How an OAK Community release is cut, what it consists of, and how anyone can check that
the artifacts they hold are the ones that were built.

## What a release is

| Artifact | Produced by | Covered by `SHA256SUMS` |
|---|---|---|
| `oak_community-<version>.tar.gz` | `make release` | Yes |
| `oak_community-<version>-py3-none-any.whl` | `make release` | Yes |
| `oak-community-<version>.cdx.json` | `make release` | Yes |
| `THIRD-PARTY-LICENCES.md` | `make release` | Yes |
| `SHA256SUMS` | `make release` | — it is the manifest |
| `SHA256SUMS.sig` | the maintainer, after the build (see [Signing](#signing-every-release-after-090)) | No — it signs the manifest |
| `build-provenance.json` | `make release` | **No** — see below |
| API and web container images | `.github/workflows/release.yml` | **Per platform**, proven by building twice — see [Images](#images) |

`build-provenance.json` records wall-clock facts about one particular build — commit,
builder platform, interpreter and `uv` versions. Including it in the manifest would make
two otherwise identical builds produce different manifests, so it sits beside the
manifest rather than inside it. It is provenance, not an integrity control.

`THIRD-PARTY-LICENCES.md` is generated from the SBOM, so it lists packages. The IBM Plex
fonts the wheel carries for the report PDF are vendored files, not a package: the
inventory names them in its preamble, their SIL Open Font License 1.1 text ships among the
wheel's licence files, and the wheel's licence is `Apache-2.0 AND OFL-1.1`.

The SBOM describes the **released runtime closure**, not a developer virtualenv. It is
generated by installing the built wheel plus the locked runtime dependencies into a
throwaway environment and scanning that, so it names the packages a consumer actually
gets — the lockfile's runtime closure is 48, including the optional `keychain` extra the
wheel can install and, since Sprint 13, `reportlab` with `pillow` and `charset-normalizer`;
nine carry environment markers, so 39 resolve on every platform and the rest depend on
it — rather than the far larger set a
contributor's development environment holds. The subject
component carries the wheel and sdist SHA-256 digests, so an SBOM cannot be silently
paired with a different build.

## Versioning

`0.9.0` is the version this tree builds. It was tagged `v0.9.0` on 2026-10-01, approved by
`nmasamba` the same day in all three roles
([release/0.9.0/release-decision.md](release/0.9.0/release-decision.md)), and **published as a
GitHub Release** that day. The tag was cut at the owner's instruction minutes before the
signatures, as `v0.8.0`'s was, and has not been moved. `0.7.1` was published on 2026-09-03
and is the release before it. `0.8.0` is tagged `v0.8.0` and was approved by `nmasamba` on
2026-09-23 in all three roles
([release/0.8.0/release-decision.md](release/0.8.0/release-decision.md)), but was **never
published**: `0.9.0` superseded it first. That tag was cut the day before its signatures,
at the owner's instruction, and has not been moved either. `0.7.0` was
approved on 2026-08-22 but never published anywhere, and was re-cut as `0.7.1` when the
pre-launch hardening work made a deliberate digest-shifting change (see `CHANGELOG.md`);
the `0.7.0` record stays as history. The `0.7.x` numbering is not `0.1.0`, and the reason
is recorded in [ADR-0002](adr/0002-release-versioning.md): `0.1.0` sorts *below* the `0.6.0.dev6`
development builds that already existed, so releasing it would have been an ordering
regression.

`VERSION` is the single source of truth. `pyproject.toml`, `STATUS.md`, `package.json`,
`web/package.json` and `openapi/oak.openapi.json` must all agree with it; `make
toolchain-check` (inside `make validate`, inside `make check`) fails if any of them
drifts. Bump `VERSION` first, then run `make validate` and fix what it names.

The compatibility rules that apply from `0.7.0` onward are in
[compatibility.md](compatibility.md).

## Cutting a release

```bash
make bootstrap
make check          # with OAK_TEST_DATABASE_URL set: see CONTRIBUTING.md
make scan-images
make release
uv run python scripts/verify_release.py --checksums-only dist/release
```

`make scan-images` builds both container images and scans them, failing on any **fixable**
CRITICAL or HIGH finding. It is not part of `make check`, because it needs Docker and
network and `make check` deliberately needs neither. Findings with no vendor fix are
reported without failing — see
[release/0.7.0/container-scan.md](release/0.7.0/container-scan.md) for why that asymmetry
is the point rather than a loophole.

`make release` refuses to finish unless three things hold:

1. **The build reproduces.** It builds twice into separate directories and compares
   digests. Reproducibility is declared in `pyproject.toml` (`reproducible = true`)
   rather than inherited from a build-backend default that could change under us.
2. **The wheel installs cleanly.** It creates a throwaway environment containing only
   the locked runtime closure plus the built wheel.
3. **The installed artifact works outside this checkout.** It runs the installed `oak`
   console script from an unrelated working directory and confirms that canonical
   schemas, the community catalogue and policy packs all resolve *from inside the
   installed package*. Every other end-to-end test runs against an editable install,
   which always finds those in the source tree — so this is the only check that
   exercises what a consumer gets.

Then tag, which triggers `.github/workflows/release.yml`:

```bash
git tag -a v0.9.0 -m "OAK Community 0.9.0"
git push origin v0.9.0
```

That workflow runs `make check` before `make release`, against a migrated PostgreSQL service
as CI does, so a release cannot be cut from a tree that fails the gate or skips the
database suites, and separately builds the API and web images twice each and compares
them (see [Images](#images)). It verifies the artifacts against their checksums only
(`--checksums-only`), because the signature is made after it.

### Signing (every release after 0.9.0)

Every release after `0.9.0` is signed: `1.0.0`, and any `0.9.x` or `0.10` cut before it.
The maintainer signs `SHA256SUMS` with an SSH key held offline, and the verifier refuses a
release without that signature unless its manifest is one of the two published unsigned
(`RR-005`). No agent creates this key or signs anything; the steps are the maintainer's.

1. **Once:** generate an Ed25519 key on a machine you control, protected by a passphrase,
   and keep the private half offline:

   ```bash
   ssh-keygen -t ed25519 -C "OAK Community releases" -f ~/.ssh/oak-release
   ```

   Pin its public half in `keys/allowed_signers` as one line,
   `<principal> <key type> <public key>` (for example
   `nmasamba ssh-ed25519 AAAA…`), in a reviewed commit that lands before the first signed
   release is tagged. That file is the only key the verifier believes.
2. **Each release:** after `release.yml` finishes, download its `release-artifacts`, check
   them with `python3 scripts/verify_release.py --checksums-only <directory>`, then sign
   the manifest in the namespace the verifier uses:

   ```bash
   ssh-keygen -Y sign -f ~/.ssh/oak-release -n oak-release SHA256SUMS
   ```

   This writes `SHA256SUMS.sig`. Run `make verify-release`'s check on the directory,
   `python3 scripts/verify_release.py <directory>`, which must now say who signed it, and
   attach `SHA256SUMS.sig` with the other files.
3. **Rotating the key** adds the new key's line to `keys/allowed_signers`, in a reviewed
   commit, and keeps the old one, so the releases it signed still verify. **Revoking** a
   key that may be compromised removes its line. Consumers take the file from the default
   branch (below), not from a release's tag, so from that commit on no release the key
   signed verifies, older ones included, until the maintainer re-signs them with a pinned
   key. A tag keeps the file as it was when the release was cut, so taking it from there
   would keep believing a revoked key.

The signature binds who released the artifacts, not how they were built: it does not
replace the reproducible build and the provenance above, and it publishes nothing to a
third party. Sigstore through GitHub's artifact attestations was considered and not chosen
for `1.0` (2026-10-28): it would write every release to a public transparency log, and its
verification needs `gh` or `cosign` and a network.

## Verifying a release

If you have the artifacts and `SHA256SUMS`:

```bash
sha256sum -c SHA256SUMS
```

On macOS, where coreutils is not installed by default:

```bash
shasum -a 256 -c SHA256SUMS
```

OAK also ships a dependency-free verifier that behaves identically on both platforms and
returns distinguishable exit codes (`0` verified, `2` mismatch, `3` manifest or file
missing or malformed, `4` signature missing, not verifying or not checkable):

```bash
python3 scripts/verify_release.py <directory> --allowed-signers keys/allowed_signers
```

It needs no OAK installation and imports nothing from OAK, because a verifier you must
install the software to run is not much use before you have decided to trust the
software. Take `scripts/verify_release.py` and `keys/allowed_signers` from the repository's
default branch, `main`, over a channel you trust independently of the download; from a
checkout, `--allowed-signers` defaults to that file. Not from the release's tag: a key
revoked since is still pinned there, and the `v0.7.1` and `v0.9.0` tags predate both the
signature check and the file. Checking a signature needs `ssh-keygen` (OpenSSH 8.2 or
later, for `-Y find-principals`), which macOS and most Linux systems include; an older one
is reported as unable to check the signature, not as a bad one. The verifier also names,
as `UNLISTED` on stderr, any file in the directory the manifest does not list:
`build-provenance.json` always is one (see above), and nothing it names is checked.

### What verification proves, and what it does not

Checksums prove that **the bytes you have are the bytes the manifest describes**.

**The signature proves who released them.** The verifier checks `SHA256SUMS.sig` with
`ssh-keygen -Y verify`, in the `oak-release` namespace, against the key pinned in
`keys/allowed_signers`, and never against a key inside the directory it is verifying. It
fails closed: a missing signature, a file with no key pinned, a signature by another key,
over another manifest or in another namespace, or no `ssh-keygen` to check it with, each
refuses the release with exit `4`.

**`0.7.1` and `0.9.0` were published unsigned**, before signing began, and are the only
releases that verify without a signature. The verifier recognises them by the SHA-256 of
the `SHA256SUMS` each was published with (the digests GitHub reports for those release
assets, pinned in the script), never by a version the downloaded files name, because
whoever controls the download controls the names; it then says the manifest is unsigned.
A signature beside one of them must still verify.
For those two, obtain `SHA256SUMS` over a channel you trust independently of the
artifacts, or compare against the digests published in the release notes: an attacker who
controls the channel you fetched from can replace unsigned artifacts *and* their manifest
together.

The refusal paths are tested: `tests/integration/test_release_verification.py` tampers with
an artifact, substitutes one of equal length, removes one, empties the manifest, points a
manifest entry outside the download directory, and, with throwaway keys generated in the
test, signs with another key, in another namespace and over another manifest, pins no key,
carries a key inside the release, and hides `ssh-keygen`, requiring a non-zero exit for
each. `RR-005` in [security/residual-risk.md](security/residual-risk.md) records what stays
open until the maintainer pins a key and signs `1.0.0`.

## Images

`.github/workflows/release.yml` builds the API and web images for `linux/amd64` **twice**,
the second time with no cached layer, on a BuildKit pinned by version and digest, and
fails unless the two builds give one image ID per image (`scripts/reproduce_images.py`,
which writes `image-reproducibility.json`). It then runs `oak --version` inside the API
image, records the image IDs, and runs `scripts/scan_images.py` — the same gate as
`make scan-images` — which emits one CycloneDX SBOM per image plus an unsigned
`image-provenance.json` into the `image-evidence` artifact, folding the reproducibility
record into the provenance, and fails the job on any *fixable* CRITICAL or HIGH finding.
Locally the same evidence lands under `docs/release/<version>/` and is committed there.
CI's `check-linux-arm64` job builds both images twice natively for `linux/arm64` on the
same pinned BuildKit, so that platform is proven on every push.

What makes two builds one image (`RR-006`, closed by Tier 3's Batch A):

- The API image takes Debian's packages, security updates included, from the dated
  `snapshot.debian.org` archive its Dockerfile names (`ARG DEBIAN_SNAPSHOT`), so the
  package set depends on that date and not on the build day. **The date moves at each
  release** (the checklist below), which is how reproducibility and `RR-036`'s updates
  coexist: a release takes the fixes published up to its snapshot, and `make scan-images`
  still decides whether the image ships.
- The web image runs on the trixie variant of the same unprivileged nginx image and takes
  Debian's packages from the same snapshot date: its Alpine variant had no dated archive to
  pin to, and the newest upstream Alpine image still carried fixable findings, so neither
  upgrading at build time nor standing still could satisfy both the proof and the scan.
- The API image's user is created with a fixed shadow date and without the account
  files' backups, and what apt, dpkg and ldconfig write with the build's clock is removed.
- Every build passes `SOURCE_DATE_EPOCH`, the source commit's time: Python compiles
  hash-based bytecode with it (the venv's `.pyc` files are compiled at build time by `uv`;
  the runtime writes none), BuildKit stamps the image configuration with it, and the
  exporter rewrites every layer's file timestamps to it (`rewrite-timestamp=true`).

Two honest caveats:

- **Images are not published.** There is no registry, no pushed tag, and no image
  digest a consumer can pull by. Building them in the workflow exists to prove they
  build — the failure mode that left the API image unbuildable for an entire sprint,
  invisible to both `make build` and CI at the time. CI now builds both images too, on
  every push (the browser suite's Compose project on x86_64, and twice in the arm64
  job), but keeps no evidence of them; this workflow builds and scans the release's own.
- **The claim is per platform and per builder.** A platform CI did not build twice, a
  build with another BuildKit, and a Compose build, which passes no source date, make no
  claim; `snapshot.debian.org` is a build-time dependency; and the base images move only
  when their digests are re-pinned. The provenance says `byte_reproducible: true` only
  from the record of two matching builds, naming the platform, the BuildKit, the
  snapshot date and both image IDs, and only when the record is about these images: the
  same platform, artifact version and source commit, a builder it names, and images the
  scan did not rebuild.

Base images *are* pinned by tag **and** immutable `sha256` digest in both Dockerfiles and
in `compose.yaml`, and `make toolchain-check` fails if the `uv`, Python, Node,
unprivileged-nginx runtime or Compose PostgreSQL pins drift, if either Dockerfile loses its
snapshot date or the two name different dates, if the source date leaves the API
Dockerfile, if a workflow builds the images without proving them twice or on an unpinned
BuildKit — and
separately if the running Python or the pnpm-provisioned Node differs from the pins.

To prove the images locally, for the platform your machine builds natively, on a builder
running the same pinned BuildKit as the workflows (Docker Desktop's default builder
refuses timestamp rewriting; the record lands beside the other evidence):

```bash
docker buildx create --name oak-reproduce --driver docker-container --driver-opt image=moby/buildkit:v0.34.0@sha256:b059f8d7226d0b326bc871af489a5dddf65e36af4d20d14251b072974d9ee87c
```

```bash
python3 scripts/reproduce_images.py --builder oak-reproduce --platform linux/arm64 --output docs/release/$(cat VERSION)/image-reproducibility.json deploy/images/api.Dockerfile deploy/images/web.Dockerfile
```

## Publication

**OAK Community `0.9.0` is published as a GitHub Release and nowhere else**, at
<https://github.com/nmasamba/OAK/releases/tag/v0.9.0>, on 2026-10-01. The six files are the ones the `v0.9.0` run of
`release.yml` produced: the wheel, sdist, SBOM, licence inventory, `SHA256SUMS` and build
provenance.
- **Before attaching:** they were verified against `SHA256SUMS`.
- **After publication:** they were downloaded again from the release and verified a second
  time.
- **Against the approved build:** the wheel is byte-identical to the one the decision
  record cites, even though that one was built on macOS and this one on Linux.

The build itself still publishes nothing; a named maintainer attached them. `0.9.0` is not
on PyPI and not in a container registry. `0.8.0` was never published.

**`0.7.1`, the release before it, was published the same way**: the six files from the
`v0.7.1` run of `release.yml` were verified against `SHA256SUMS` and attached to
<https://github.com/nmasamba/OAK/releases/tag/v0.7.1> on 2026-09-03. PyPI and a container
registry each remain a separate decision.

Consequently there are published artifacts to substitute and a release page to
poison, which is exactly why the verification instructions above matter: obtain
`SHA256SUMS` over a channel you trust independently of the artifacts, and remember that
checksums prove the bytes match the manifest, not who produced them (`RR-005`). Every
release after `0.9.0` also carries the maintainer's signature over `SHA256SUMS`.

## Release checklist

- [ ] `VERSION` bumped; `make validate` green (this catches every file that must agree)
- [ ] `CHANGELOG.md` has a section for the version, including any digest-shifting change
      called out as such
- [ ] `make check` green with `OAK_TEST_DATABASE_URL` on a fresh, migrated database — verified
      by reading the output, not the exit code; it names any PostgreSQL-gated test it skipped
- [ ] `make scan-images` green — no *fixable* CRITICAL or HIGH in either image
- [ ] `ARG DEBIAN_SNAPSHOT` in both Dockerfiles moved to the release day, so the release
      takes the security updates published since the last one; `make scan-images` green
      on the result, and the release's `image-reproducibility.json` says `reproduced: true`
- [ ] Reference-case byte-stability verified directly against the previous mainline
- [ ] `openapi/oak.compatibility-baseline.json` rewritten from the release's contract
      (`python scripts/check_openapi_compatibility.py --write-baseline`), with the
      unreleased lists in `tests/unit/test_openapi_compatibility.py` emptied. Otherwise
      the gate goes on guarding an older release's contract
- [ ] `make release` green, including its reproducibility and clean-install gates
- [ ] The `release.yml` artifacts verified against their checksums
      (`scripts/verify_release.py --checksums-only`)
- [ ] `SHA256SUMS` signed by the maintainer with the key pinned in
      `keys/allowed_signers` (`ssh-keygen -Y sign -n oak-release`), and
      `python3 scripts/verify_release.py <directory>` green, naming the signer
- [ ] Known limitations published and current
      ([security/residual-risk.md](security/residual-risk.md))
- [x] Named maintainer, security and licence approvals recorded — see
      [release/0.9.0/release-decision.md](release/0.9.0/release-decision.md). This is a
      human decision and cannot be self-approved by the person or agent doing the build.
      `nmasamba` signed all three rows for `0.9.0` on 2026-10-01, minutes after the tag was
      cut at the owner's instruction. The record says so. Publication is a separate
      decision, and for `0.9.0` it was taken the same day
