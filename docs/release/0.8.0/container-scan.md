# Container image scan — OAK Community 0.8.0

The `0.8.0` scan, run from a clean tree at `07880eb` after Sprints 9 and 10 merged. No base
pin moved, and the only Dockerfile change since `0.7.1` creates the owner-only model-state
directory in the API image (`install -d -m 0700`), which installs no package. The scanned
package set is therefore the `0.7.1` one rebuilt today, and what differs below is what the
scanner's database now says about it rather than what the image contains. The superseded
`0.7.1` record is at [../0.7.1/container-scan.md](../0.7.1/container-scan.md).

Reproduce with:

```bash
make scan-images
```

scanner from the same exported tarball as the vulnerability scan, so they describe the
image that ships — including its final-stage base — not a build stage.

## What moved since 0.7.1, and why

Two changes, in opposite directions, and neither is a change to the image:

- **The three CRITICALs are gone.** At `0.7.1` all three were in `perl-base`. Debian has
  since published fixes, and the image's build-time `apt-get upgrade` installs them, so a
  rebuild today carries them. `perl-base` still accounts for one HIGH (`CVE-2026-9538`).
- **HIGH rose from 13 to 44**, entirely from advisories published after the `0.7.1` scan
  and entirely without vendor fixes. Four `util-linux` advisories — `CVE-2026-76642`,
  `CVE-2026-78408`, `CVE-2026-78409` and `CVE-2026-78410` — are each reported against the
  nine packages Debian builds from that one source (`bsdutils`, `libblkid1`,
  `liblastlog2-2`, `libmount1`, `libsmartcols1`, `libuuid1`, `login`, `mount`,
  `util-linux`), which is 36 of the 44. One `systemd` advisory (`CVE-2026-16742`) accounts for
  `libsystemd0` and `libudev1`, one `ncurses` advisory for the four `ncurses` packages,
  and `libacl1` and `perl-base` carry one each.

The count is therefore a count of *package instances*, not of distinct defects: the 44
HIGH findings are eight distinct advisories. That is worth stating plainly, because a
reader comparing 13 to 44 would otherwise conclude the image got substantially worse when
what happened is that one source package's advisories are counted nine times.

This residue is the set `RR-036` records. The API image is Debian-based and inherits its
distribution's patch cadence; rebuilding picks up whatever Debian has published, which is
why the scan is a release step rather than a pinned artefact.

The web image — `nginxinc/nginx-unprivileged:1.29.1-alpine`, running as uid 101 — reports
**no findings at any severity**, unchanged from `0.7.1`.

## The gate

Unchanged: `make scan-images` fails on **fixable** CRITICAL or HIGH findings and reports
unfixable ones without failing, `tests/contract/test_image_scan_gate.py` pins both halves,
and the gate stays out of `make check` because it needs Docker and network. The release
workflow's `images` job runs this same script, so a fixable finding fails the release build
as well as this local run.
